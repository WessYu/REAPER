# REAPER threat model

**Status:** implementation-backed baseline, not a claim of complete mitigation
**Reviewed against:** `main` at `1554402e0676e11dbc7958a7d6ea242b4315c5ea` plus this branch's signed-scope, replay, journal/recovery, persistent audit, tenant/RLS, runner-isolation contract, trust-store, rule-pack and supply-chain changes
**Scope:** Node.js CLI/library, local review server, static analysis of scanned projects, PostgreSQL catalog introspection, runtime verification, and authorized attack mode. Hosted control plane, remote multi-user service, operating-system sandboxing, and commercial release infrastructure are outside the current runtime.

## System and trust boundaries

- **Untrusted inputs:** scanned source and SQL, REAPER configuration, HTTP/DNS responses, command-line paths, PostgreSQL catalog contents, and caller-provided rule callbacks.
- **Trusted operator inputs:** exact target allowlist, acknowledgement/reference, environment classification, expiry, budgets, mutation opt-in, and declared cleanup steps. Strict attack runs verify an Ed25519 scope against a trusted-key source and atomically consume the scope nonce before execution. Private-key custody and production key distribution remain external responsibilities.
- **Local process boundary:** CLI/library `runAttack` executes in-process; `runAttackJob` launches the trusted engine in a child process with a filtered environment, temporary working directory, Node heap limit, bounded IPC and an external deadline. Cancellation is sent to the engine so it can attempt declared cleanup; force-kill follows a separately bounded cleanup grace. Static scanning parses source and does not run it. Custom Rule SDK callbacks are executable trusted JavaScript in-process.
- **Network boundary:** attack mode resolves the approved origin, blocks prohibited address classes, pins requests to a resolved address, disables automatic redirects, enforces origin checks, request/rate/time limits, and checks DNS stability. These controls do not replace an egress firewall or isolated runner.
- **Data boundary:** findings and runtime audit omit configured credential values. Reports can still contain paths, route names, schema metadata, resource labels, and operator-authored strings and must be handled as sensitive assessment artifacts.
- **Persistence boundary:** strict runner mode requires persistent state for write-ahead cleanup journals, replay records and a hash-chained audit log. The built-in filesystem stores are local-process foundations with exclusive locking, integrity validation and bounded reads/writes; horizontally scaled production deployments require a shared durable backend and reviewed storage controls.

## Priority gaps

The following remain outside the guarantees of this repository revision and must not be presented as already solved:

1. **OS-enforced runner isolation is DEPLOYMENT-DEPENDENT.** Strict mode fails closed without a provider that advertises process, filesystem, network and enforceable resource limits, but the built-in process provider is not a sandbox. A production provider/runtime must actually enforce those capabilities.
2. **Shared production state is DEPLOYMENT-DEPENDENT.** Filesystem journal, replay and audit stores are implemented for the local foundation; multi-runner/horizontally scaled deployments need a reviewed shared durable backend and backup/retention policy.
3. **Private-key custody and managed secret infrastructure are DEPLOYMENT-DEPENDENT.** Trust-store lifecycle/revocation checks are implemented, but private signing keys, KMS/HSM integration and hosted secret-vault leasing are external.
4. **Hosted identity/control-plane API is NOT IMPLEMENTED.** The organization/workspace/project domain, authorization boundary and PostgreSQL RLS schema exist, but there is no hosted SSO/session service or internet-facing multi-user API in this repository.
5. **Arbitrary third-party JavaScript rules are not sandboxed.** Signed commercial rule packs are data-only; the separate Rule SDK remains trusted local code by design.
6. **Release attestation emission depends on trusted tag/release context.** PR CI validates package, SBOM, hashes and release-evidence expectations; GitHub attestations are emitted only by the tag workflow with OIDC permissions.
7. Independent penetration testing, architecture review, deployment hardening review, incident-response readiness, monitoring and a real-world pilot remain external requirements before strong commercial maturity claims.

Until those deployment and external-review requirements are satisfied, REAPER must not be described as 100% secure, enterprise certified, or a penetration-test replacement. A successful scan, score, or authorized runtime scenario does not establish that a target is secure.
